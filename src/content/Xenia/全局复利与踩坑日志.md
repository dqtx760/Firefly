## 2026-08-17 - Cloudflare Workers（wrangler）部署静态站点全流程：保存页清理、custom domain 与 legacy route 选择、资产直出

### 场景
把桌面保存的 HTML 页面（会员充值服务页，含 CSS/二维码等本地资源）部署到自有域名 `https://plus.dqtx.cc/`，域名 DNS 已走 Cloudflare 代理，要求替换原有页面。使用 wrangler 4.120 + OAuth（账户 sphinx30@126.com）。

### 错误 / 弯路
1. 浏览器保存的页面（.html + _files 目录）夹带约 200KB 扩展注入垃圾：plasmo-csui、沉浸式翻译、截图插件样式、Notab、EDM 下载按钮、原站 CF beacon 脚本。不清理直接部署，线上会出现悬浮按钮、错位样式和原站统计脚本。
2. `wrangler.toml` 的 `assets.run_worker` 字段在 wrangler 4.120 不被支持（报 "Unexpected fields found in assets field"），直接删掉即可——worker 本身就是入口，默认先执行。
3. custom domain 路由写成 `pattern = "plus.dqtx.cc/*"` + `custom_domain = true` 被拒：Custom Domains 不允许通配符和路径，pattern 必须是裸域名 `plus.dqtx.cc`。
4. 改对 pattern 后绑定仍失败（code 100117）：`plus.dqtx.cc` 已有外部管理的 A/CNAME 记录，custom domain 系统要求先删除该记录才能接管。
5. 想删 DNS 记录但 OAuth token 只有 `zone (read)` 权限：`GET /zones/{id}/dns_records` 直接 403（DNS 记录接口需要 DNS 读权限），dashboard 删记录又必须用户手动操作。
6. 部署中途出现一次 `fetch failed`（本机有代理环境变量，网络抖动），误以为配置问题。

### 根因分析
1. 保存页面 = 页面本体 + 浏览器扩展注入的 DOM/样式/脚本，两者混在同一个 HTML 里，必须区分后再上线。
2. Workers Custom Domains 要求 hostname 的 DNS 记录由 Workers 系统自动管理；已存在的 A/CNAME 记录（哪怕指向 Cloudflare 代理 IP）也会触发 100117。
3. wrangler 的权限边界由 OAuth scope 决定：`zone (read)` 能查 zone 元信息、不能动 DNS；DNS 变更需要 Zone→DNS→Edit。
4. **legacy zone route（`[[routes]] pattern = "host/*" zone_id = ...`）在边缘层拦截该 hostname 的全部请求交给 Worker，不依赖也不修改 DNS 记录**——这是"域名已有记录 + 无 DNS 权限"场景下的正解。

### 解决方案 / 正确做法
1. **部署前清理保存页**：用脚本按锚点切掉扩展垃圾（plasmo-csui、arclet、ssbtn 样式块、CF beacon 脚本、notab shadow host、bottomBar、EDM 按钮、immersive-translate 弹窗），并断言 `chrome-extension`/`plasmo`/`immersive-translate` 等关键词 0 残留。本页从 218KB 瘦到 13KB。桌面源文件保留不动，部署副本放独立目录。
2. **部署目录结构**（`D:\客户交付流程\已部署\plus-dqtx会员站\plus-dqtx-site\`）：
   - `public/index.html`（清理后的页面，资源相对路径保持 `./xxx_files/...` 原样）
   - `public/<原 _files 目录>/professional.css`、`contact-qrcode.webp`（只复制实际引用到的文件）
   - `worker.js`：`export default { async fetch(request, env) { return env.ASSETS.fetch(request); } }`
   - `wrangler.toml`：

```toml
name = "plus-dqtx-site"
main = "worker.js"
compatibility_date = "2025-01-01"
assets = { directory = "./public", binding = "ASSETS" }
[[routes]]
pattern = "plus.dqtx.cc/*"
zone_id = "5d0f86b59a70a5cd7229ecefe4729988"
```

3. **域名绑定决策链**：
   - 先 `wrangler whoami` 确认登录与 scope。
   - 用 `GET /api.cloudflare.com/client/v4/zones?name=<域>`（OAuth token 从 `%APPDATA%\xdg.config\.wrangler\config\default.toml` 读）确认 zone 归属和 zone_id；DNS 记录列表接口无权限时用 `nslookup` 观察。
   - 优先尝试 custom domain（`pattern = "裸域名"` + `custom_domain = true`）；报 100117 且无 DNS 写权限时，改用 legacy zone route（`pattern = "域名/*"` + `zone_id`），**无需动 DNS**。
4. **验证闭环**：线上 curl 首页 + 资源（含空格/中文的路径要 percent-encode），核对字节数与本地一致；grep 关键内容标记（品牌、按钮文案、教程/质保区块）和垃圾关键词 0 残留；CSS 校验自定义规则（如 `.notice-flat`）已生效。
5. 遇到 `fetch failed` 先重试一次，别急着改配置。

### 未来复用
- 以后部署保存页面 / 静态站点到 Cloudflare 的固定流程：
  1. `wrangler --version` + `wrangler whoami`（确认 OAuth 与 scope）。
  2. 清理扩展垃圾 → 建 `public/` + `worker.js` + `wrangler.toml`（assets 直出 + legacy route）。
  3. `wrangler deploy`，报错按 100117/权限/网络三类分别处理。
  4. curl 验证首页、资源字节数、关键内容标记。
- **记住**：域名已有 DNS 记录且 token 无 zone 写权限 → 不要纠结 custom domain，直接 legacy zone route。
- 部署目录固定复用：改源文件（`D:\客户交付流程\已部署\plus-dqtx会员站\Chat.Gpt Plus 等会员服务 _ 文文AI.html`）后，`cd D:\客户交付流程\已部署\plus-dqtx会员站\plus-dqtx-site && python build.py && wrangler deploy` 即可。
- token 若要完整能力，建议在 Cloudflare dashboard 签发 Zone:DNS:Edit 的 API token，可走 custom domain 并自动管理 DNS。

把长期知识库目标目录和项目本地经验目录混为一谈，误以为一开始只要在 Obsidian/Fuwari 里建一个统一文件夹，Project Cairn 就会直接把所有项目经验同步进去。

## 2026-08-10 - Mac 代理冲突：机场客户端 SSE 流式连接阻断与 Clash 端口 7890 错配排错

### 场景
解决 macOS 客户使用 AI 工具（Codex / Work Body）时网络报错的问题。问题表现为：使用自研机场客户端时 Work Body 端口报错、切换 Clash 后 Chrome/Codex 全面断网、卸载 Clash 换回机场客户端时 Codex 在对话中频繁弹出 `stream disconnected before completion`（重新连接 2/2）报错。

### 错误 / 弯路
1. 客户之前切换到 Clash 时，由于系统代理开启但没在 Proxies 中手动选中绿色的可用节点，导致 Chrome 无法访问网页，进而对 Clash 产生不信任，卸载并换回了机场定制客户端。
2. 卸载重装 Clash 时，其 Mixed Port 会默认重置为 `7897`（或其他默认端口），而 Codex `.env` 或环境变量已写死为 `7890`，如果不手动对齐，Codex 依然会无法使用。
3. 认为机场客户端“好用且能访问网页”即可支持 AI 终端。忽略了机场自研客户端底层通常只管普通的 HTTP 网页分流，对大模型 API 常用的长连接/流式 SSE（Server-Sent Events）协议及 SSL/TLS 命令行握手支持极差，从而导致 stream disconnected 的报错。

### 根因分析
1. **Work Body 端口依赖**：Work Body 默认必须在本地 `7890` 建立通信，机场客户端不占用 `7890` 导致其直接报错。
2. **机场自研客户端协议限制**：为了节省网关连接资源，机场专属客户端会在中间掐断长时间的流式大模型 SSE 长连接。
3. **Clash 节点未选定**：Clash 默认系统代理拦截全网，如果不手动测速选好可用节点，全网流量会在本地直接断连。
4. **端口错配**：Clash 的 Mixed Port 与 Codex 中配置的环境变量（`HTTP_PROXY` 等）不一致，导致网络不通。

### 解决方案 / 正确做法
1. **统一代理工具**：彻底卸载/退出机场自研客户端，统一安装开源的 Clash (Verge / Nyanpasu)。
2. **手动对齐端口**：确保在 Clash 设置（Settings/Mixin）中将 Mixed Port 设为 `7890`，与 Codex 配置（如 `.env` 中的 `HTTP_PROXY="http://127.0.0.1:7890"`）保持一致。
3. **手动选定有效节点**：在 Clash 的代理（Proxies）页面中测速，手动选择一个绿色延迟的有效节点，解决“Chrome 网页打不开”的用户痛点。
4. **开启 TUN 模式**：通过 Clash 的 TUN 模式强制接管全网所有命令行流量（Codex），避免代理分流规则遗漏。

### 未来复用
- 遇到命令行大模型工具弹出 `stream disconnected` 或连接超时重试时，首要检查是否使用的是自研机场软件，如果是，必须劝说其换为 Clash 并选择可用节点。
- 对齐端口是客户端与代理软件协作的核心。配置好代理后，必须在终端用 `lsof -i :7890` 验证是否由代理进程监听。

## 2026-07-30 - Codex 调用飞书 CLI：Hermes 误识别、最小授权与 Wiki 并发写入

### 场景

在 Codex 桌面任务中，使用本机已有的 `lark-cli` 用户配置，向飞书知识库「技术笔记 / 项目（Projects）」创建项目模板中心和多个子模板。

### 错误 / 弯路

1. `lark-cli` 检测到 `HERMES_HOME` 后，要求绑定 Hermes；直接绑定又因 Hermes `.env` 缠少 `FEISHU_APP_ID` 而失败。
2. 一开始把问题理解成飞书应用未配置，但本机 `C:\Users\Administrator\.lark-cli\config.json` 实际已有可用应用和用户身份。
3. 搜索知识库时缺少 `search:docs:read`，不能定位「技术笔记」。
4. `docs +create --wiki-node` 创建出的仍是 Drive 文档，没有直接出现在 Wiki 节点列表里。
5. 并发向同一 Wiki 父节点创建多个子节点，部分请求返回 `131009 lock contention`。

### 根因分析

1. Codex 运行外部命令时带入了 Hermes 环境变量，`lark-cli` 出于身份隔离策略优先按 Hermes 上下文处理。
2. 飞书用户登录状态、应用配置、OAuth scope 和 Wiki 节点位置是四层独立状态，不能混为一谈。
3. 飞书同一父节点的结构写入存在锁竞争，不适合并发创建子节点。

### 解决方案 / 正确做法

1. 只在当前 PowerShell 子进程中临时移除 `HERMES_HOME` 和 `HERMES_GIT_BASH_PATH`，不修改系统环境变量：
   `Remove-Item Env:HERMES_HOME -ErrorAction SilentlyContinue`。
2. 复用本机已有 `lark-cli` 用户配置，不重新创建应用、不暴露密钥。
3. 缺少搜索权限时，仅申请 `search:docs:read`，不申请无关 scope。
4. 用 `wiki +space-list` 定位知识库，用 `wiki +node-list` 确认父节点和子节点。
5. 创建 Wiki 内容优先使用 `wiki +node-create` 建节点，再用 `docs +update` 写正文。
6. 已创建成 Drive 文档时，用 `wiki +move --obj-type docx --obj-token <token> --target-space-id <space> --target-parent-token <parent>` 移入 Wiki。
7. 同一父节点下的 `wiki +node-create` 必须串行执行；出现 `131009` 后先检查是否已创建，再单次重试，避免重复页面。
8. 最后用 `wiki +node-list` 和 `docs +fetch` 双重读回，验证层级、标题和正文。

### 未来复用

- 遇到 Hermes 绑定提示时，先检查本机是否已有独立 `lark-cli` 配置，再决定绑定，不要直接重配应用。
- 飞书授权遵循最小权限原则：缺哪个 scope，只补哪个 scope。
- 飞书目录结构写入默认串行；正文写入不同文档后才考虑并发。
- Wiki 交付的完成标准是：节点在正确父级、正文可读回、关键字段存在。

## 2026-06-27 - 飞书知识库与口播脚本批量生产避坑：CLI 参数、编码、代码块与验证

### 场景
围绕「Codex APP 指南」飞书知识库做了一轮连续内容生产和维护：

1. 用飞书 CLI 读取/更新知识库文档。
2. 根据官方 Codex 指南补充知识库内容。
3. 新建 30 天、50 条短视频口播选题文档。
4. 批量清理提词器代码块里的「钩子 / 痛点 / 解决方案 / 金句」说明词。
5. 在本地 Markdown 文件里沉淀提示词。
6. 将内容写入飞书并读回验证。

### 错误 / 弯路
1. 一开始把用户说的「避坑指南」理解成必须有同名文件，忽略了根目录已有的 `全局复利与踩坑日志.md` 就是用户实际想维护的避坑文档。
2. 用 PowerShell `Get-Content` 直接读取中文 Markdown 时，终端显示乱码，容易误判为文件编码损坏。
3. 批量清理代码块时，最初只删除独立成行的 `钩子：`、`痛点：` 等标签，但有些内容可能是「标签 + 正文」同一行，导致清理不彻底。
4. 在 PowerShell 中直接把中文正则传给 `node -e`，中文字符可能被命令行编码影响，导致正则匹配失败。
5. 在 PowerShell 中写包含 Markdown 三反引号的 `node -e` 正则时，反引号会被 PowerShell 当作转义字符处理，导致代码块正则没有匹配到任何内容。
6. 飞书 CLI 帮助显示 `docs +create` 使用 `--markdown`，但实际当前版本校验要求 `--content`，第一次新建文档失败。
7. 飞书 CLI 的 `--content @file.md` 在 PowerShell 中容易触发 splatting 或参数解析问题，必须写成 `--content '@file.md'`。
8. 写入飞书后，如果只看本地文件，很容易以为成功；但飞书转换 Markdown 后可能出现格式变化，必须读回验证。
9. 读取飞书时使用 `--format markdown`，当前 CLI 版本提示 unknown format 并 fallback 到 json，不能依赖这个参数一定返回纯 Markdown。
10. 创建大量内容时，如果不先做本地结构检查，容易出现 Day 数量、代码块数量不匹配。

### 根因分析
1. 用户说的文件名可能是功能性称呼，不一定是精确文件名；需要先在根目录里识别等价文件，如「踩坑日志」「避坑指南」「复利记录」。
2. Windows PowerShell 的默认输出编码和文件实际 UTF-8 编码不一致，中文显示乱码不代表文件坏了。
3. PowerShell 对反引号、`@file`、中文命令参数都有特殊解析风险。
4. CLI 帮助文档和实际版本行为可能不一致，尤其是本地工具版本较旧时。
5. 飞书文档写入是外部系统状态，必须用「写入 -> 读回 -> 关键词/结构验证」闭环确认。
6. 批量生成内容时，人工肉眼抽查不够，要用脚本验证关键结构。

### 解决方案 / 正确做法
1. 维护根目录避坑内容时：
   - 优先使用 `D:\zed-workspace\全局复利与踩坑日志.md`。
   - 如果用户说「避坑指南」，先检查是否指这个文件，不要急着新建 `避坑指南.md`。
   - 新记录插到「记录区（倒序排列）」下面，保持最新在最上方。

2. 读取中文 Markdown 时：
   - 不用 PowerShell `Get-Content` 判断中文是否正常。
   - 优先用 Node 按 UTF-8 读取：

```powershell
node -e "const fs=require('fs'); const s=fs.readFileSync('D:/path/file.md','utf8'); console.log(s.slice(0,800));"
```

3. 处理 Markdown 代码块时：
   - 避免在 PowerShell 命令里直接写三反引号正则。
   - 可以用 `String.fromCharCode(96).repeat(3)` 生成三反引号。
   - 对代码块做按行解析，比复杂正则更稳。

4. 清理提词器代码块说明词时：
   - 不只删除独立标签行，也要处理 `标签：正文` 同一行。
   - 正确逻辑是：
     - 识别包含 `钩子：`、`痛点：`、`解决方案：`、`金句：` 的代码块。
     - 对每一行去掉这些标签前缀。
     - 删除空行。
     - 保留正文，一句一行。

5. 在 PowerShell 中调用飞书 CLI 写入本地文件内容时：
   - `@file` 必须加引号。
   - 正确示例：

```powershell
lark-cli docs +update --as user --api-version v2 --doc <doc_token> --command overwrite --doc-format markdown --content '@file.md'
```

6. 新建飞书文档时：
   - 当前 CLI 版本实际使用 `--content`，不要只相信 `--help` 里的 `--markdown`。
   - 正确示例：

```powershell
lark-cli docs +create --as user --api-version v2 --wiki-space <space_id> --wiki-node <parent_node_token> --title "标题" --content '@file.md'
```

7. 写入飞书后必须读回验证：
   - 用 `lark-cli docs +fetch --as user --api-version v2 --doc <doc_token>`。
   - 检查：
     - 文档标题是否正确。
     - Day 数量是否正确。
     - 代码块是否存在。

### 批量生成 Obsidian 文章专栏双链（2026-07-23）

## 2026-08-03 17:46｜apply_patch 导致文件内容翻倍的根因与修复方案

**场景**：使用 pply_patch 工具对 Markdown 文件做多处替换（给18条笔记各加一行 - [ ] 自己实践），操作后文件内容变成原来的两倍——原文18条变成36条，相当于整个文件被追加了一遍。

**根本原因（已确认）**：

pply_patch 是基于"上下文匹配 + 差量替换"的工具。当补丁中的上下文行在文件中**多次出现**（本例中 - [ ] 待发布 出现了18次），工具的匹配逻辑可能将整个文件当作未匹配段，采用"追加新版本"而非"原地替换"的方式写入，导致原内容+新内容同时存在于文件中。

**触发条件**：
1. 补丁的上下文行（context lines）与文件中的多行高度重复，工具无法唯一定位
2. 补丁范围过大（跨越全文），工具回退到全文覆写模式
3. 文件较长且结构高度重复（如多条结构相同的 checklist 条目）

**正确做法——对重复结构批量修改，优先用 PowerShell 字符串替换**：

`powershell
# 读取文件（UTF-8）
 = Get-Content "路径" -Raw -Encoding UTF8

# 精确替换（用 .Replace() 或 -replace，不用 apply_patch）
 = .Replace("旧字符串", "新字符串")

# 验证替换结果
 = [regex]::Matches(, '目标模式').Count
Write-Host "替换后数量: "

# 写回（UTF-8 无 BOM）
[System.IO.File]::WriteAllText("路径", , [System.Text.UTF8Encoding]::new(False))
`

**修复方案**：
- 文件内容翻倍时，找到第二次出现的标题位置，截取前半段即可还原
- 用 $content.IndexOf("标题文本", 偏移量) 精确定位分割点

**经验总结（决策规则）**：
- ✅ pply_patch：适用于**结构唯一、上下文不重复**的精准定点修改（如改某个函数、某段唯一标题下的内容）
- ✅ PowerShell .Replace() / -replace：适用于**批量替换重复模式**（如给多条 checklist 加行）
- ❌ 不要用 pply_patch 对"多处结构相同的文本块"做批量操作——极易触发全文重写

- `/v1/models` 从超时变为 HTTP 200（6.2s 返回）

`@bitkyc08/opencodex` 原生支持 `config.proxy` 配置项，写入后 `applyProxyEnv()` 在启动时自动设置 `HTTP_PROXY`/`HTTPS_PROXY`，并给 `NO_PROXY` 追加 `localhost,127.0.0.1` 以保持健康检查正常。

- 诊断链路：`/healthz` → `/v1/models` → 直连上游 → 走代理上游。前两步定位网关自身状态，后两步定位代理配置。
