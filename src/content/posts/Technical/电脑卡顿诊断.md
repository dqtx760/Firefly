最近我的电脑有一些卡顿，我以为是内存占用过高导致的,.我刚刚让我的AI去做了一些诊断，其中发现了一些问题

先说明一下，我这是一台 Windows 11 25H2 的精简系统，而且是打了鸡血的洋垃圾

---

## 诊断结论

**内存根本不是瓶颈。**

| 指标 | 实测 |
| --- | --- |
| 物理内存 | 128 GB |
| 已用 | 34% |
| 可用 | 86.1 GB |
| 待机缓存 Standby | 76.7 GB（可回收，不算真占用） |
| 磁盘空闲率 | 98.8% – 99.8% |
| 页面文件读取 | 0.5 – 2.5 次/秒 |

任务管理器里那个"内存占用高"的数字，绝大部分是**待机缓存**——系统把读过的文件缓存在内存里备用，随时可以回收。不用加内存，也不用清内存。

**真正的原因是 CPU 被白白烧掉了。** 一个僵尸进程长期吃满 1 个核，一个终端空转再吃掉 0.5～0.9 个核。这台机器一共就 20 个逻辑核，被吃掉 2 个就是 10% 的算力。

---

## 优化措施

### 1. 关闭 LANDrop + 禁止自启

**做法**：先结束进程，再删掉自启项。

```powershell
Stop-Process -Name LANDrop -Force -ErrorAction SilentlyContinue
Remove-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run' `
  -Name 'app.landrop.landrop-v2-electron' -ErrorAction SilentlyContinue
```

**原因**：LANDrop 有个渲染子进程变成孤儿（父进程 PID 9344 已不存在）后开始疯狂空转，**累计烧掉 16.9 小时 CPU**（存活仅 28 小时，平均已占满 60% 一个核）。实测连续多轮 95.7% / 97.5% / 98.8% 一个核心。

已排除"它在干活"的可能：没有窗口、无输入响应、磁盘和网络 IO 均为 0——纯自旋。

**状态**：进程已结束（当前 0 个在运行）。**但自启项还在**，下次开机还会自动跑起来，需要执行上面第二条命令。

### 2. 刷新率改 60 Hz 以上

我这个电脑的刷新率最高是 180，但是到 AI 指出这一条，我打开之后发现，我设置的是最低的。

我突然想起来，前段时间为了让 OBS 录屏的性能提升，我把刷新率调到了最低，这可能是我电脑卡顿的重要原因。我把它恢复到 180 之后，电脑瞬间就不卡顿了。

**状态**：✅ 已完成（59 Hz → 180 Hz，实测已生效）

> 补充：如果以后录屏时 180 Hz 确实影响性能，正确的做法是在 OBS 里单独调低**显示器采集**的帧率，而不是把整个系统的刷新率降下来。系统刷新率影响的是你日常所有操作的流畅度。

### 3. 重启 wezterm 终端

**做法**：用**任务管理器**关掉它，然后重新打开。

1. 按 `Ctrl+Shift+Esc` 打开任务管理器
2. 在"进程"里找到 `wezterm-gui`
3. 右键 → 结束任务
4. 重新打开终端

**原因**：wezterm 在**完全没有任何输出、完全空闲**的情况下仍在烧 CPU，属于程序自身的 bug。实测两轮隔离采样（45 秒 / 60 秒，期间零输出）都稳定在 40% 以上，典型值 70%–86% 一个核心。

**为什么用任务管理器而不是命令**：这个 wezterm 正是承载当前对话窗口的宿主终端（进程树 `wezterm-gui → nu → omp`）。如果用命令结束它，窗口会连带正在运行的任务一起立刻关闭。

**状态**：❌ 未处理，仍在空转（实测 49.5% 一个核心，累计 0.87 小时）

> 重开之后如果新终端仍然持续占用 80% 以上，说明是 wezterm 与这台机器的兼容问题，可以升级 wezterm 或改用 Windows Terminal。

### 4. 重启资源管理器

**做法**：

```powershell
Stop-Process -Name explorer -Force
Start-Process explorer
```

**原因**：explorer 已经连续运行 2 天，句柄和线程不断累积，外壳变迟钝。当前有 **3 个实例**，句柄数在 1238 / 5623 / 8463 之间分布。重启会清理掉这些累积。任务栏和桌面会消失 2–3 秒后自动恢复，属正常现象。

**状态**：❌ 未处理

> 如果任务栏没自动回来：任务管理器 → 文件 → 运行新任务 → 输入 `explorer.exe` → 确定。

### 5. 保留一个常用的远程软件

**做法**：任务管理器 → **启动应用** 标签页 → 对不常用的点右键 → **禁用**。

**原因**：这些远程控制/串流软件各自都装了虚拟显示器驱动，并挂钩桌面合成器（dwm）。dwm 累计已消耗 17 小时 CPU，平均占 14% 一个核，偏高。多个叠加是主要原因之一。不需要卸载，只是不再开机自启。

**状态**：
- `SunloginService` —— Running / Auto ❌ 待处理
- `AskLinkService` —— Running / Auto ❌ 待处理
- `GameViewerService` —— 已不存在（应该已经卸载了）✅

### 6. 内存压缩

**检查命令**：

```powershell
Get-MMAgent
```

**当前状态**：`MemoryCompression : True` —— **已经是开启的**。

> 注：如果是在 16:38 检查时发现是关闭的，那么执行 `Enable-MMAgent -MemoryCompression` 后已经生效——Memory Compression 进程启动于 16:41:03，与启用时间吻合。
>
> 容易看错的地方：输出里的 `PageCombining : False` 是**页面合并**，和内存压缩是两个不同的功能，别把这一行当成压缩开关。

**实话**：这台机器 128 GB 内存只用 34%，内存压缩在这里基本不会带来可感知的改善——它只在内存紧张时才有意义。开着没坏处，但别指望它解决卡顿。

## 不要动的东西

### ❌ Power 服务（保持禁用）

Power 服务当前是 `Stopped / Disabled`。**不要去启用它。**

一开始 AI 建议我恢复这个服务，我凭直觉觉得不对劲——我这台是打了鸡血的，万一启用了把频率打回原样怎么办。实测下来我的判断是对的，但机制和我想的相反：

| 检查项 | 实测 |
| --- | --- |
| Power 服务状态 | **Stopped / Disabled**（即当前状态） |
| CPU 此刻频率 | **2530 – 3538 MHz**，全部高于标称 2301 |
| 平均有效频率 | **3099 MHz** |
| 7 天内电源相关报错 | **0 条** |

**为什么关着不影响**：打鸡血的 turbo-unlock 是 **BIOS / 微码层补丁**（微码版本 0x3F02），直接在硬件层解锁倍频，**不经过 Windows 电源管理**。证据很直接——现在服务是禁用状态，CPU 照样跑到 3538 MHz。

> 这一点和我之前写的 [X99-F8D + Win11 打鸡血](/posts/technical/x99-f8d--win11-打鸡血/) 能对上：那篇里打鸡血是「刷写修改版 UEFI 固件，改写 CPU 睿频规则，放开功耗与电压限制」，并且要在 BIOS 里设置 C-State。全程都在固件层完成，Windows 侧什么都不用做。

**真正的风险恰恰在"启用"这一步**：Power 服务一旦启动，Windows 才会去套用电源方案；而方案里的「最大处理器状态」正是能压制超频的那个开关。查了注册表，当前 8 个电源方案的**处理器子组全是空的**，也就是没有任何上限。启用后如果被套上默认的 100% 上限，反而可能把倍频压回官方档位。

**关闭它的代价**：仅影响睡眠 / 休眠 / 显示器超时。而休眠本来就是关的（`HibernateEnabled = 0`），实际无损失。

### ⚠️ CPU 核心数与超线程（建议先别动）

E5-2696 v3 官方规格是 **18 核 / 36 线程 / 45 MB L3**，我这里是 **10 核 / 10 线程 / 45 MB L3**。

| 项目 | 官方规格 | 我这台 |
| --- | --- | --- |
| 核心数 | 18 | **10** |
| 线程数 | 36 | **10**（超线程关闭） |
| L3 缓存 | 45 MB | 45 MB（吻合） |

这是典型的「**关核换频率**」打法——BIOS 里关掉部分核心、关掉超线程，让剩下的核心能跑到更高倍频。实测平均 3099 MHz（高于官方全核睿频 2800 MHz）就是这个取舍换来的。

**如果进 BIOS 打开超线程，很可能反而让倍频掉下来，得不偿失。** 除非确实需要更多线程（多开、编译、虚拟机），否则保持现状。

验证命令：

```powershell
Get-CimInstance Win32_Processor |
  Select-Object DeviceID, NumberOfCores, NumberOfLogicalProcessors
```

### ❌ 不要做 DISM 组件修复

检查发现 `C:\Windows\WinSxS\Backup` 是**空的（0 项）**，组件存储的备份已被精简掉；系统里也没有安装镜像（ISO / WIM）可作为修复源，WinRE 也不存在。

DISM 的 `/RestoreHealth` 找不到修复来源，只会白等很久然后失败。**这一项在精简系统上无解，跳过。**

### ❌ 不用管那些 Windows 更新报错

系统日志里每小时都有十几条更新服务报错（事件 7000 / 7023），但这是精简系统的正常现象——Windows 更新组件已被裁掉：

| 文件 | 状态 |
| --- | --- |
| `wucltux.dll` | 缺失 |
| `wuwebv.dll` | 缺失 |
| `wuuhext.dll` | 缺失 |
| `MoUsoCoreWorker.exe` | 缺失 |
| `wuaueng.dll` | 只有 180 KB（正常约 2.5 MB） |

这些报错不影响日常使用，也修不了，忽略即可。
